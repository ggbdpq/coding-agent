# rcode 学习指南

> 面向"会 Rust 基础但没手写过 agent"的读者。所有路径都指本仓库真实文件，
> 建议边读边开对应源码对照。

## 一句话定义

rcode 是一个几百行一层、总共约两千行的 Rust 程序：把你输入的一句话发给模型 API，
模型要调工具（读文件/改文件/跑命令）就替它执行、把结果喂回去，循环到模型给出最终回答——
**一个带手脚的 chat 循环，就是 coding agent 的全部秘密**。

## 三个核心要素（配生活类比）

| 要素 | 在哪里 | 类比 | 一句话 |
| --- | --- | --- | --- |
| agent loop | `src/core/agentloop.rs` 的 `run_turn` | 返工循环 | 甲方（模型）改图需求（tool_calls）→ 你执行并把图（tool 消息）交回去 → 直到甲方说"就这样"（没有 tool_calls） |
| SSE 流式解析 | `src/providers/sse.rs` 的 `sse_data` | 逐行接水 | HTTP 响应像一根不断流的水管，SSE 用空行把水流切成一杯一杯（事件），每杯里 `data:` 开头的才是水 |
| trait 即插座标准 | `src/kernel/types.rs` 的 `ChatClient` | 万国插座 | agentloop 只认"能 chat 的插座"，OpenAI/Anthropic 两种插头各自实现，换插头不动电器 |

## 点破最常见误解

**误解："Rust 写个 HTTP 客户端/agent 必须上 tokio + reqwest + hyper 全家桶。"**

不对。同步阻塞 + `ureq` 一把梭就够，本仓库就是完整证据：
`src/providers/openai.rs` 的整个 HTTP 调用就是 `agent.post(url).set(...).send_string(&body)`
一行，流式读取就是 `resp.into_reader()` 套 `BufReader` 逐行读。agent 的瓶颈是模型出
token 的速度（秒级），不是并发连接数——async 在这里解决的是一个不存在的问题，
代价是 `Rc` 全部换成 `Arc`、回调全部要 `'static`、颜色函数都要写进 async 上下文。
什么时候 async 才值：你要同时服务几百个会话（web 服务形态）时。

**误解二："所有权会让消息流转很难写。"**

想清楚一件事就够了：消息只有一份正文归属，方向永远是 `Vec<ChatMessage>`（对话历史）
往外的只读借用 + 构造新消息 push 进去。看 `src/core/agentloop.rs` 的 `run_turn`——
它拿 `&mut Vec<ChatMessage>`，push 助手消息前先把 `tool_calls` `clone` 出来
（因为 push 之后原数组的借用就没了），这是整个项目唯一的"所有权小坎"。

**误解三："Rust 没有闭包参数多态，插件系统肯定要写一堆泛型魔术。"**

不需要。四类插件就是一个枚举（`src/kernel/plugin.rs` 的 `Plugin`），
回调全是 `Rc<dyn Fn(&Value) -> String>`——动态分发在单线程 REPL 里完全够用，
比泛型方案少一整套类型参数传染。

## 结合本仓库举例（建议阅读顺序）

1. **先看线格式**：`src/kernel/types.rs` 的 `ChatMessage::to_value`——OpenAI 线格式
   `"role"/"content"/"tool_calls"` 怎么用 `serde_json::Map` 手工拼出来（不引 derive）。
   会话文件（`src/core/session.rs` 的 `append`）和 API 请求体用的是同一个方法。
2. **然后看循环**：`src/core/agentloop.rs`——40 轮上限、工具错误以 `"错误：..."` 文本回流、
   熔断后不带工具再要一次总结，三件事都在一个 for 循环里。
3. **再看一个最薄的插件**：`src/plugins/tools/read.rs`（30 行工具壳）对照
   `src/plugins/tools/edit.rs`（`apply_edit` 纯函数 + 工具壳分离，单测只测纯函数）。
4. **然后看安全边界**：`src/core/permission.rs`（三态闸门，`always` 置 yolo）+
   `src/shell/repl.rs` 的 `ReplAsk`（壳只做 UI 适配）+
   `src/plugins/tools/netguard.rs`（web_fetch 的 SSRF 判定表）。
5. **最后看装配**：`src/main.rs`（60 行）——注册清单 → `create_app` → 起 shell，
   理解 `kernel 不 import core`（session/systemprompt 都是 main 注入的）。

## 行业对比

| 维度 | 手写（本仓库） | 框架（langchain 等） |
| --- | --- | --- |
| 调试 | 断点打在 `run_turn` 一层栈内看到全部状态 | 穿多层抽象，栈里全是回调注册 |
| 协议演进 | 新协议 = 一个 provider 插件文件 + 清单一行 | 等框架适配，或自己写适配层（写完发现框架是负担） |
| 适合场景 | 学习原理、千行级工具、行为要完全可控 | 快速拼原型、需要现成 RAG/记忆组件 |

| 维度 | 同步阻塞（本仓库） | async |
| --- | --- | --- |
| 代码形状 | 从上到下顺序读，`thread::sleep` 就是等 | `async/await`、`Send` bounds、`tokio::select!` |
| 单会话延迟 | 无差别 | 无差别（瓶颈在模型） |
| 多会话并发 | 每会话一线程（够用到几百） | 万级连接才拉开差距 |
| 何时值 | CLI 工具、单用户本地 agent（本仓库定位） | web 服务、批量离线任务 |

## 下一步路径

1. 跑通 `cargo test`，读 `tests/smoke.rs` 的 `script_response`——假 SSE 服务器怎么按
   "最后一条消息角色"分场，这是无网络调试 agent 的通用手法。
2. 照着 `src/plugins/tools/todo.rs` 加一个你自己的工具（一个文件 + `src/plugins/mod.rs`
   清单一行），体验插件模型。
3. 读 `src/providers/anthropic.rs` 的 `to_anthropic_request`——同一条内部消息怎么映射成
   另一种协议（system 顶层、tool_result 块、相邻同角色合并），理解"内部形状"为什么值钱。
4. 进阶：给 rcode 加第二个壳（单发模式 `rcode -p "问题"`，跑完即退）——
   只写 `src/shell/` 下一个新文件，验证"换壳不动核心"不是空话。
5. 对照阅读：`../tcode/`（行为规格的 TypeScript 原文）、`../gocode/`（Go 形态）、
   `../pcode/`（Python 形态）——同一份规格三种语言，diff 着看收获最大。
