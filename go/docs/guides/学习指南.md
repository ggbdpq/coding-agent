# 学习指南：从会 Go 到手写过 agent

面向读者：会 Go 的语法和常用标准库，但没亲手写过 agent。读完你能用自己的话讲清
"一个 coding agent 由什么组成"，并能在这仓库里指出每一部分对应的文件。

先给结论：**agent = 用模型 API 的 function calling 驱动一个"模型↔工具"循环，
外加把每一步流式画到终端上**。没有魔法，剩下的都是工程。

## 1. 一句话定义

coding agent 是一个循环：把用户的话发给模型 → 模型要么直接回答、要么点名要某个工具 →
本地执行工具、把结果塞回对话 → 再问模型，直到它不再要工具（`internal/core/agentloop.go` 的
`RunTurn`，60 行）。

## 2. 三个核心要素与生活类比

| 要素 | 生活类比 | 本仓库落点 |
| --- | --- | --- |
| agent loop | 返工循环：你（模型）是外包设计，每次交稿都被甲方（工具结果）打回改，直到验收通过；40 轮熔断 = 合同封顶，最后不带工具再要一次总结 | `internal/core/agentloop.go` |
| SSE 流式解析 | 用 `bufio.Reader` 逐行接水：服务器不停滴水，你按空行把水按杯分好，只留 `data:` 开头的那些杯 | `internal/providers/sse.go` 的 `SSEData`，消费方在 `openai.go`/`anthropic.go` |
| 接口即插件 | 插座标准：`kernel.ToolDef`/`ChatClient` 就是墙上的插座孔位，任何符合孔位的电器（工具/协议）都能插上，不用改墙 | `internal/kernel/plugin.go` + `internal/plugins/plugins.go` 清单 |

## 3. 最常见误解，逐个点破

| 误解 | 事实 | 本仓库证据 |
| --- | --- | --- |
| "Go 写 CLI 必须 cobra" | 手写 `os.Args` 判断 + 一段 usage 字符串就够，命令少时 cobra 是纯税 | `cmd/gocode/main.go`，`--help/--version/--yolo` 共 30 行 |
| "HTTP 客户端必须上框架/生成器" | `net/http` + `encoding/json` 手写 POST 和 SSE 足够，双协议客户端各约 150 行 | `internal/providers/openai.go`、`anthropic.go` |
| "并发能力必须 goroutine 池" | agent 的主干是同步阻塞的请求-响应链，goroutine 只干 stderr 收集、封顶拷贝这类小活；上了池反而难排错 | 全仓只有输出拷贝处用了 goroutine |
| "流式解析很难" | SSE 本质是"空行分事件、`data:` 前缀取值"的文本协议，`bufio.Reader.ReadString('\n')` 十几行写完 | `internal/providers/sse.go` |
| "插件系统要反射/注册中心" | 一个 struct 值（`Plugin`，四选一字段）+ 一个切片（`Registry`）就是插件系统，显式清单比魔法扫描可读 | `internal/kernel/plugin.go` |

## 5. 手写 vs 框架，什么时候值

| 场景 | 取向 | 理由 |
| --- | --- | --- |
| 学习原理 / 面试 / 教学仓库 | 手写（本仓库） | 每一层都能讲清楚；SSE、function calling、上下文管理这些考点藏在 60-200 行的实现里 |
| 单二进制分发、依赖洁癖 | 手写 | `go.mod` 零 require，`go build` 即交付，无供应链面 |
| 快速验证产品想法 | 框架（langchain-go、eino 等） | 现成的记忆/工具/多模型适配，换来的是黑盒与依赖树 |
| 长期维护的生产 agent | 手写核心 + 少量标准库 | agent 的核心其实很小；框架的抽象更新频率常高于你的业务 |

判断口径：**当第三方库替你写的部分 < 你为理解它付出的部分时，手写更便宜**。agent 恰好在这个交点附近。
