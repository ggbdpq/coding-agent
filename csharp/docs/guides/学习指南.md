# 学习指南：可取消性（CancellationToken 与三态 Ctrl+C）

> 对应实现：ccode（C# / .NET 8）。读完你应该能回答：为什么 ccode 的 Ctrl+C 能做到
> "流式中=真取消请求、确认中=拒绝本次、空闲=退出"而进程不死，其他三版为什么做不到。

## 1. 一句话定义

**可取消性 = 用一个可传播的"取消信号"对象（CancellationToken）贯穿一次操作的完整调用链，
让链路上每个阻塞点都能及时、干净地停下来，而不是靠杀死进程或假装没听见。**

## 2. 核心要素与生活类比

| 要素 | 类比 | 在 ccode 里的落点 |
| --- | --- | --- |
| `CancellationTokenSource`（CTS） | 总闸：拉一次闸，整栋楼断电 | 每轮对话开一个：`shell/Repl.cs` 里 `turnCts = new CancellationTokenSource()` |
| `CancellationToken` | 各家各户的分闸接口：只读"有没有断电"，自己决定怎么停 | `ChatOptions.CancellationToken`、`ToolPlugin.RunAsync(args, ct)` 的第二个参数 |
| `ct.IsCancellationRequested` / 抛 `OperationCanceledException` | 看到断电就安全停机，不硬扛 | `providers/OpenAi.cs` 的 `SendAsync(..., ct)`、`Sse.DataAsync` 的 `ReadLineAsync(ct)` |
| `CancellationTokenSource.CreateLinkedTokenSource` | 总闸 + 楼层定时闸串联：任一跳闸全楼断电 | `plugins/tools/WebFetch.cs` 的 20s 超时闸与用户总闸串联 |
| `Console.CancelKeyPress` 的 `e.Cancel = true` | 不让整栋楼炸掉，先接住警报再分诊 | `shell/Repl.cs` 注册的三态路由处理器 |
| `LineSource.Interrupt()` | 给正在等电梯的人送一张"取消电梯"的纸条 | `shell/Repl.cs`：把 Ctrl+C 变成当前等待者收到的一个空行事件 |

关键认知：**令牌是"广播"，不是"命令"**。CTS 只负责广播取消状态；每一段代码收到广播后
自己选择怎么停（抛异常、返回部分结果、清理后退出）。这就是 .NET 的"协作式取消"。

## 3. 点破两个常见误解

| 误解 | 事实 |
| --- | --- |
| "C# 写工具必须上 ASP.NET/宿主框架才有 DI、配置、取消那一套" | console 模板 + BCL 内置类型就够。ccode 全程只有 `dotnet run`：`Console.CancelKeyPress` 是 `System` 内置事件，CTS 是 `System.Threading` 内置类型，HttpClient/System.Text.Json 都是 BCL。ccode.csproj 一个 PackageReference 都没有（见 `ccode.csproj`） |
| "取消 = 杀进程（Ctrl+C 只能让程序死）" | 那只是默认行为。`e.Cancel = true` 接住事件后，杀不杀、杀多大范围完全由你决定。ccode 三态路由（`shell/Repl.cs`）就是反例：同一次 Ctrl+C，空闲才退出，流式中只取消 HTTP 请求，确认中只拒绝一次操作 |
| （附带）"取消令牌要穿到哪里就一层层手写转发，很脏" | 转发链本身就是调用图的可视化：ccode 里令牌从 `ReplShell` → `Turn.RunUserTurnAsync` → `AgentLoop.RunTurnAsync` → `ChatOptions` → `SendAsync`/`ReadLineAsync`，这条链恰好就是"一个用户轮次"的物理边界。与其藏进 AsyncLocal 魔法，不如让它可见 |

## 4. 本仓库的真实实现（读代码顺序）

按这条链读，每一步都能在文件里找到成员名：

1. **事件的接住与路由** — `shell/Repl.cs`
   `Console.CancelKeyPress += (_, e) => { e.Cancel = true; ... }`：权限确认中
   （`askActive == true`）→ `lines.Interrupt()`；回答流式中（`turnCts != null`）→
   `turnCts.Cancel()`；空闲 → `lines.Interrupt()`，而 REPL 主循环把 `Text == null` 的
   `LineEvent` 当作退出指令。
2. **令牌的诞生** — 同文件：`turnCts = new CancellationTokenSource()` 在轮开始时创建、
   `finally` 中 `Dispose`；令牌作为 `Turn.RunUserTurnAsync(..., turnCts.Token)` 传入。
3. **令牌的旅行** — `core/Turn.cs` → `core/AgentLoop.cs`：令牌装进
   `ChatOptions.CancellationToken`，随 `deps.Provider.ChatAsync(messages, options)` 下行。
4. **真正的取消点 1：HTTP 流** — `providers/OpenAi.cs` / `providers/Anthropic.cs`：
   `SharedHttp.Client.SendAsync(request, HttpCompletionOption.ResponseHeadersRead, ct)`；
   之后 `Sse.DataAsync(stream, ct)`（`providers/Sse.cs`）里 `reader.ReadLineAsync(ct)` ——
   Ctrl+C 一按，正在等待下一个 SSE 事件的读循环立刻抛 `OperationCanceledException`。
5. **真正的取消点 2：子进程** — `plugins/tools/Bash.cs`：
   `CancellationTokenSource.CreateLinkedTokenSource(cancellationToken)` + `CancelAfter(120s)`，
   超时或取消都走 `KillTree`（win32 `taskkill /pid /T /F`）；区分"用户取消"（抛
   `OperationCanceledException` 交给断尾修复）与"超时"（返回 `exit=timeout（…）` 文本）。
6. **不重试取消** — `providers/Retry.cs`：`catch (OperationCanceledException) { throw; }`
   排在可重试异常之前——用户按了 Ctrl+C，退避 1s/2s 的重试没有意义。
7. **善后：断尾修复** — `core/Turn.cs` 的 `RepairTail`：取消可能留下"assistant 带着工具调用
   却没有 tool 回应"的断尾，补 `（用户中止，未执行）` 占位并照常 `AppendSince` 落盘，
   下一轮请求对 API 依然合法；随后异常继续上抛，REPL 打印"（本轮已中止…）"。
8. **权限确认中的取消** — `shell/Repl.cs` 的 `ReplPermissionUi.AskAsync`：
   等待用户输入用 `lines.WaitAsync()`；Ctrl+C 被路由成 `Interrupt()` 后，等待者收到
   `Text == null` 的事件 → 返回 `PermissionDecision.Deny`，模型收到"用户拒绝了本次操作"。

一句话总结这条链：**CancelKeyPress 是接线员，CancellationToken 是电线，LineSource 是
"当前谁在等输入"的花名册；断尾修复是断电后的应急照明。**

## 5. 行业对照：四种语言怎么解决同一个问题

| 语言/实现 | 取消原语 | ccode 同族实现的实际表现 |
| --- | --- | --- |
| C#（ccode） | `CancellationToken` 协作式取消，语言与 BCL 全链路内建（HttpClient/Stream/Task 全都吃令牌） | 三态语义完整：请求级真取消 + 确认拒绝 + 空闲退出，进程不死 |
| TypeScript（tcode） | `AbortController`/`AbortSignal`，fetch 原生支持 | 同样能真取消（`providers/openai.ts` 传 `signal`）；但 Node 终端的 SIGINT 要靠 readline 事件接住，接不住就进程退出 |
| Go（gocode） | `context.Context` 显式贯穿一切函数签名 | `internal/providers/retry.go` 对 `context.Canceled` 不重试，但 v1 的 REPL 轮中 Ctrl+C 直接退进程（README 已知局限）——信号路由没接进轮循环 |
| Rust（rcode 同规格） | 无运行时，同步 read 阻塞在系统调用上 | 同步模型没有天然的取消注入点，要么进程级信号处理，要么把 IO 全改 async（tokio + select）——代价大，干脆做不了干净版 |

规律：**取消能力 = 运行时把"取消"当作一等公民贯穿 IO 的程度**。C# 和 Go 的运行时都把
取消做进了 IO 原语（令牌 / context），差别在 GUI/终端信号层要不要你手动接线；
TS 靠事件循环 + AbortSignal；纯同步 Rust 则连注入点都要自己造。
