# 00 · 评审：借鉴什么、不借什么

> 思维模型：**第一性原理**（先回答 agent 运行时到底需要哪几个控制点）→ **奥卡姆剃刀**（只借能消除已证实缺陷的部分）→ **YAGNI**（没有需求就不借）→ **保持独立思考**（框架做得不如我们的地方，就保留自己的）。

## 1. 第一性原理：一个 coding agent 运行时只需要回答 5 个问题

| 问题 | langchain.js 1.x 的答案 | coding-agent 现状（develop） | 差距 |
|---|---|---|---|
| ① 每次调模型之前，要不要改上下文？ | `beforeModel` 钩子（summarization / contextEditing 挂在这里） | 只在每轮开始前改一次（`turn.ts:32`） | **控制点位置不对** |
| ② 模型的输出合不合法？ | `AIMessage.tool_calls` + `invalid_tool_call` + `response_metadata.finish_reason` | 解析失败就变 `{}`，不看 finish_reason | **错误被吞掉** |
| ③ 工具执行前要不要问人？问到什么粒度？ | `humanInTheLoopMiddleware({ interruptOn: { [tool]: { allowedDecisions } } })` | 三态闸门；`always` = 整个会话免审批（`specs/permission.md` R3 锁定的有意设计） | **只有两档**：允许一次，或整个会话全放开（含 bash） |
| ④ 什么时候停？停了之后怎么办？ | `modelCallLimit` / `toolCallLimit`：`threadLimit` / `runLimit` + `exitBehavior` | 硬编码 40 轮；到上限后静默再总结一次 | **不可观测、不可配置** |
| ⑤ 进程崩溃后能从哪里恢复？ | checkpointer：图的每个 super-step 存一次 | 一轮结束才 append | **持久化粒度太粗** |

结论：五个差距**都不是缺功能，而是控制点挂错了层**。修法是把控制点从"轮"下沉到"每次模型调用 / 每次工具调用"。

## 2. 借鉴清单（只借语义，自己实现）

| langchain.js 设计 | 源码位置（langchainjs） | 在 coding-agent 中的落点 | 工作包 |
|---|---|---|---|
| 中间件生命周期 `beforeModel / afterModel / wrapToolCall` | `libs/langchain/src/agents/middleware/types.ts:534-604`（钩子定义）、`agents/middleware.ts`（createMiddleware） | `core/middleware.ts`，**固定顺序组合，不进插件注册表**（尊重"loop 不插件化"的 Q4 决策） | WP1 |
| `contextEditingMiddleware` + `ClearToolUsesEdit` | `agents/middleware/contextEditing.ts` | 治理第一步：先把旧工具输出清成占位符（保留参数）——成本最低、不需要调模型 | WP2 |
| `summarizationMiddleware`（trigger / keep） | `agents/middleware/summarization.ts` | 治理第二步：compact 改成每次模型调用前都检查；摘要里保留工具调用和结果的配对 | WP2 |
| `invalid_tool_call` 内容块 | `libs/langchain-core/src/messages/tool.ts`、`content/tools.ts` | `parseToolArgs()` 返回失败时**不执行工具**，回灌带原始参数的错误消息 + 发 `tool_error` 事件 | WP3 |
| `finish_reason` 归一化 | `response_metadata`、各 provider 的 block translator | `CompletionResult.finishReason`（openai `length` / anthropic `max_tokens` 统一成 `length`） | WP3 |
| `humanInTheLoopMiddleware.interruptOn` | `agents/middleware/hitl.ts` | 新增第四态 `scoped`（"本会话允许此类"），只对**授权键**生效：默认是工具名，bash 是命令首词；`always` 原契约不变 | WP4 |
| `modelCallLimit` / `toolCallLimit` + `exitBehavior` | `agents/middleware/modelCallLimit.ts`、`toolCallLimit.ts` | 限额中间件：可配置，触发时发 `limit` 事件；强制总结那次调用同样经过治理 | WP5 |
| checkpointer（每步持久化） | `@langchain/langgraph` | 每产生一条消息就立即 append；加载会话时修复断尾 | WP6 |
| `internal/standard-tests`（用消费方视角做集成测试） | `internal/standard-tests/src/**` | 给 conformance 新增 SC-005…SC-010 场景，配一个可编排脚本的 fake provider | WP7 |

## 3. 保留的长板（框架不如这里，不要"对齐"）

| 长板 | 为什么比 langchain.js 好 | 处理 |
|---|---|---|
| 只在第一个字节到达前重试（`providers/retry.ts`） | `modelRetryMiddleware` 重试的是整次调用。流式输出到一半时重试，可能重复吐 token（推断，置信度中） | 写进 provider spec，作为 WP1 中间件**不得**重试模型调用的约束 |
| 中断后的断尾修复（`turn.ts:73-85`） | langchain 依赖 checkpointer 回放，没有显式补占位 | WP6 复用同一个函数，加载会话时也调用 |
| specs → conformance → 五版裁决链 | 框架只有单语言测试 | 每个工作包都必须带 spec 修订和场景 |
| Plan Mode 拒绝写操作 | 框架没有内置 | WP1 中迁移成 `wrapToolCall` 中间件，行为不变 |
| 写目录白名单 `skipPermission` | HITL 没有"按参数信任"的能力 | WP4 保留，和授权键并存 |
| 零依赖 | — | 所有工作包禁止新增运行时依赖 |

## 4. 明确不借（YAGNI / 违背项目定位）

- LangGraph 图运行时、`StateGraph`、`Command` / `interrupt` 的图语义：当前单循环足够，引入会破坏五版同构。
- LCEL / Runnable 管道、callbacks 体系：已有 `AgentEvent` 单一事件出口，更简单。
- `modelFallbackMiddleware`、`modelRetryMiddleware`：前者暂无需求，后者与"只在首字节前重试"冲突。
- 结构化输出 `responseFormat`、多 agent / subagent、向量记忆：没有当前需求。
- 完整的标准内容块体系（image / audio / citation 等）：只引入 `finishReason` 和 `tool_error` 两个最小概念。
- 并发执行工具（`ToolNode` 用 `Promise.all`）：串行是 spec R8 的有意设计，和权限审批交互简单。暂不改。

## 5. 一句话

> **langchain.js 1.x 的价值不在 API，而在"控制点放在每次模型调用前后"。** coding-agent 已经有正确的事件出口和裁决链，只差把控制点下沉一层。
