# 01 · 目标架构

## 1. 分层落点（遵守 ARCHITECTURE.md，不新增层）

```text
kernel/types.ts      + FinishReason、CompletionResult.finishReason、AgentEvent 新变体（WP0）
kernel/plugin.ts     + ToolPlugin.grantKey?(args)（WP4，可选字段，旧工具零改动）
core/middleware.ts   新文件：TurnMiddleware 接口 + 组合器（WP1）
core/agentloop.ts    runTurn 在固定位置调用钩子；不再内联 Plan Mode（WP1）
core/toolargs.ts     新文件：parseToolArgs（WP3）
core/governance.ts   新文件：governContext() = 清理旧工具输出 → 压缩 → 裁剪（WP2）
core/limits.ts       新文件：限额中间件（WP5）
core/permission.ts   授权键作用域（WP4）
core/turn.ts         组装中间件；每产生一条消息就持久化（WP6）
core/session.ts      加载会话时修复断尾（WP6）
providers/*.ts       回传 finishReason（WP3）
shell/web.html|repl  渲染新事件、审批按钮文案（WP4/WP5，各自只加分支）
```

依赖方向不变：`kernel ← core ← shell`，core 不 import providers/plugins 的实现。

## 2. 中间件管线（runTurn 内部）

```text
for round in 0..maxRounds:
    ┌ beforeModel*   ← governance(WP2) → limits(WP5)   可返回 {jumpTo:'summarize'|'end'}
    │ provider.chat(messages, {tools})                 ← 重试仍只在 provider 内、首字节前
    └ afterModel*    ← (预留，如 finishReason 检查)
    if 没有 tool_calls: return
    for call in tool_calls (串行，spec R8):
        parseToolArgs(WP3) 失败 → 错误 tool 消息 + tool_error 事件，跳过执行
        wrapToolCall 洋葱（外 → 内）: planMode(WP1 迁移) → [用户中间件] → permissionGate(固定最内层，不可移除) → tool.run
到达上限 → limit 事件 → 强制总结调用前同样执行 beforeModel（治理）
```

设计约束：

1. **中间件不进 Registry**。由 `turn.ts` 按固定顺序组装，不开放给插件动态注册（遵守"loop 不插件化"的 Q4 决策；安全边界不可替换）。
2. **权限闸门永远在最内层**。任何中间件都不能绕过它。Plan Mode 在外层，所以被拒的写操作不会弹审批。
3. **钩子只拿到受控的状态对象**（`TurnState`）。修改 `messages` 必须走 `replaceMessages()`，以便统一校验不变式和持久化。
4. **中间件不得调用 `provider.chat` 重试**。需要调模型的（只有压缩摘要）走 `state.callModel()`，它不带工具、计入用量、发 usage 事件。

## 3. 消息完整性不变式（所有改写上下文的代码都必须满足）

| 编号 | 不变式 | 谁会破坏 | 校验点 |
|---|---|---|---|
| I1 | `messages[0]` 永远是 system | 压缩、裁剪 | `assertInvariants()` |
| I2 | 每个带 `tool_calls` 的 assistant 消息，后面必须紧跟对应 id 的全部 tool 消息，不多不少 | 裁剪、清理、断尾 | 同上 |
| I3 | 本轮用户消息（`mark` 位置）不得被删除或摘要 | 轮内治理 | 同上 |
| I4 | 清理只替换 tool 消息的 `content`，不删除消息、不改 `tool_call_id`、不改 assistant 里的参数 | WP2 第一步 | 单测 |
| I5 | 每次改写后必须 `store.checkpoint(messages)`，持久化与内存一致 | WP2 / WP6 | 集成测试 |

`assertInvariants(messages, mark)` 放在 `core/middleware.ts`，测试与开发模式下每次 `replaceMessages` 后调用。

## 4. 事件模型增量（向后兼容）

- 已有的 `trimmed`、`compact` 事件**保留**，新增可选字段 `at: 'turn_start' | 'model_call'`。旧的壳忽略这个字段也不会出错。
- 新增 `context_edit`（清理旧工具输出）、`tool_error`、`limit` 三种事件。壳遇到不认识的事件类型时必须忽略（当前两个壳都满足：repl 的 switch 有 default 分支，web 的 renderLog switch 不匹配即跳过）。
- `TurnEndReason` **不新增取值**：到达上限后仍以 `completed` 结束，原因由 `limit` 事件表达，避免改动所有壳。

## 5. ADR-003 草案（WP0 提交到 `docs/adr/ADR-003-轮内控制点.md`）

```markdown
# ADR-003 轮内控制点：中间件钩子下沉到每次模型调用

状态：提议
背景：上下文治理、熔断、权限、持久化都只挂在"轮"这一层；一轮最多 41 次模型调用，复现可见单轮 tokens 从 9 涨到 160145（附录 A）。
决策：
1. core 引入 TurnMiddleware（beforeModel / afterModel / wrapToolCall），由 turn 固定顺序组装，不进注册表；
2. 权限闸门固定在最内层；Plan Mode 迁移为中间件，行为不变；
3. 治理 = 清理旧工具输出 → 压缩 → 裁剪，每次模型调用前都执行；
4. 参数非法不再静默变 {}（修订 agent-loop R4）；
5. 审批新增第四态 `scoped`，按授权键记忆（permission R2 增量；R3 的 always 语义不变）；
6. 每产生一条消息就持久化（修订 session-turn）。
后果：五版需同步；过渡期 conformance 新场景对非 TS 版登记 ALLOW_DIFF，直到完成移植。
否决的方案：直接依赖 langchain（破坏零依赖与五版同构）；LangGraph 图运行时（YAGNI）。
```
