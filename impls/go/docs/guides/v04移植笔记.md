# v0.4 移植笔记：tcode R4/R5 与 v0.4 第一批 → gcode

面向读者：对照着 tcode（TypeScript 参照实现）读 gcode（Go 标准库版）的人。
先给结论：**本次把 tcode 的 R4（审批策略 + 写白名单）、R5（usage 事件）与 v0.4 第一批
（compact 尾部保留、80% 双档治理、exec 无交互、@引用、--continue、/sessions、/init）
移植进 gcode，版本 0.3.0 → 0.4.0，`go test ./...` 全绿（含新增冒烟场景 H）。**
只移植 v0.3→v0.4 范围：tcode 已是 v0.5.0，其 Plan Mode / apply_patch / Skill 索引 /
diff 预览一律不碰。

## 2. Go 惯用表达与 tcode 的差异点

| tcode（TS） | gcode（Go） | 为什么 |
| --- | --- | --- |
| `skipPermission?:` 可选方法 | `SkipPermission func(...) bool` 可 nil 函数字段 | Go 没有可选方法；nil 字段即"未声明"，agentloop 判 nil 后走闸门 |
| `onUsage?: (usage: {prompt_tokens...}) => void` | `OnUsage func(usage Usage)`，`Usage` 是双 int struct | 具名 struct 可演化（加 total_tokens 不改签名），比匿名对象可读 |
| `messages.splice(1, tailStart-1, summaryMsg)` | `make` 新切片，三段 append（system/摘要/尾部） | Go 的 `append(messages[:1], ...)` 会共享底层数组、踩坏原历史；compact 的纪律是"失败原封不动"，重建切片最稳 |
| `contextLimit * 0.8`（浮点） | `int(float64(limit) * 0.8)` | ContextLimit 是 int，显式收窄一处完成，不引入浮点配置 |
| `path.delimiter` 分隔 + resolve 后过滤空串 | `os.PathListSeparator` 分隔，**先滤空段再 filepath.Abs** | tcode 的空段过滤在 resolve 之后，而 `path.resolve('')` 返回 cwd——`ALLOW_WRITE=a;;b` 会把 cwd 静默收进白名单；Go 版把过滤提前堵掉这个洞 |
| `readFile: (p) => string \| null` | `func(p string) (string, bool)` | Go 惯例用 ok 布尔区分"读不到"与"空文件"，不用 nil string |
| `process.exitCode = failed ? 1 : 0` | `os.Exit(1)` | exec 分支自己收尾；REPL 的强制退出同样用 `os.Exit(130)`，项目内已有一致先例 |
| `--approval normal\|never` CLI 旗标 | 不移植旗标；`GCODE_APPROVAL` 环境变量 + `/approval` 命令 | 任务范围只要求 env + 命令；少一个旗标少一套"参数规整跳过 -- 值"的解析 |
| approval 只在装配时消费（`yolo || approval==='never'`） | 同语义保留，且 `/approval never` 运行时**同步 `Yolo.Value`** | 闸门只认 `Yolo.Value`；不同步的话 /approval never 是"假生效"。normal≡关、never≡开，与 /yolo 语义互锁 |
| 正则替换回调带分组 `replace((_all, lead, rawPath) => ...)` | `ReplaceAllStringFunc` 内再 `FindStringSubmatch` 取分组 | Go 标准库的回调不携带子匹配，二次匹配是零依赖前提下的最短路径 |
| REPL 与 exec 各自内联 cappedRead | `core.ReadCapped` 一份共享 | 两处消费（`internal/shell/repl.go`、`cmd/gcode/main.go`），复制会漂移 |

## 3. 踩坑记录

1. **openai usage 分片会被 choices 判空吃掉**。`stream_options.include_usage` 的 usage
   分片 `choices` 为空，而移植前的代码先 `if len(chunk.Choices) == 0 { continue }`——
   usage 解析若放在判空之后永远收不到。必须先消费 usage 再判空
   （`internal/providers/openai.go` attempt 内有注释锚点）。
2. **尾部切片点的扫描方向以测试断言为准**。任务文本写"从 len-4 向前扫描"，
   但 `tcode/test/compact.test.ts` 的断言是：len-4 恰为 tool 消息时，尾部从 idx7 的
   user 开始、总长 5 条——即**从 idealStart 向后**扫最近的 user（`pickTailStart` 的
   `i++`）。两个方向都能"配对安全"，保留条数却不同；照抄断言，不照抄描述。
3. **Go 无判别联合的 usage 事件**沿用项目既有的扁平 `AgentEvent`：`PromptTokens`/
   `CompletionTokens` 字段 v0.3 已立契约，本次只是开始填值，消费端接口零改动。
4. **Windows 测试路径**：白名单单测用 `t.TempDir()`（已归一化绝对路径）构造两侧，
   避免 chdir，也避开 `filepath.Abs` 与大小写不敏感文件系统的纠缠——判定逻辑本身
   与 tcode 一致是大小写敏感前缀比较，两端同病，不做平台特判。
5. **anthropic usage 字段是"每次事件给增量/累计值"**而非 openai 的"流末一个分片"：
   message_start 给 input/output 初值，message_delta 给累计 output。移植沿用 tcode
   的逐事件回调（`internal/providers/anthropic.go`），不做合流后再上报的"优化"。

## 4. 与 tcode 的行为差异（有意为之）

- `/approval` 是 gcode 新增命令（tcode 只有 CLI 旗标）；切换时同步 yolo 开关（见上表）。
- `GCODE_ALLOW_WRITE` 空段不收 cwd（tcode 会，见上表）；其余优先级
  （config.json `allowWriteDirs` 优先于环境变量）与 tcode 一致。
- bash/web_fetch 两端都不设白名单：命令级操作无法按路径约束，逐次确认不放松。
- usage 事件两端 REPL 均不渲染（静默消费）；exec 渲染器同样忽略，仅事件流可观测。
- atrefs 的截断按 rune 计（tcode 按 UTF-16 码元），ASCII 场景数值一致，CJK 更准。
