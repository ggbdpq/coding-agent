# 学习指南：事件模型与上下文压缩（R1 + R3）

> 面向"会用 Python，但没手写过 agent 事件流"的读者。所有路径都是本仓库的真实位置
> （版本 v0.3.0），可直接打开对照；行号会漂移，以成员名为准定位。

## 1. 一句话定义

**事件模型 = turn 循环干活时不再直接调 UI，而是把"发生了什么"打包成一个个小对象，
通过一个 `emit` 回调递出去；上下文压缩 = 长对话装不下时，调一次模型把全部旧历史换成
一条摘要消息。** 前者解决"核心逻辑被终端打印代码淹没"（`pcode/core/turn.py` 的
`run_user_turn` 只发事件，一行 `print` 都没有）；后者解决"长会话把 token 预算撑爆"
（`pcode/core/compact.py` 的 `compact_context`，失败时原历史一个字都不动）。

## 2. 三个核心要素（配生活类比）

| 要素 | 类比 | 一句话 | 代码位置 |
| --- | --- | --- | --- |
| AgentEvent | 法庭书记员 | 庭审（turn）里发生的每件事——证人发言（text_delta）、出示证物（tool_call/result）——书记员逐条记下（emit）；旁听席（壳/审计/回放）只看记录，不上诉台插话。事件类型清单就是记录模板：`pcode/kernel/types.py` 的 `TurnStart`/`User`/`TextDelta`/`ToolCallEvent`/`ToolResult`/`Permission`/`Trimmed`/`Usage`/`TurnEnd` | `pcode/kernel/types.py`（类型）、`pcode/core/turn.py` 的 `run_user_turn`（唯一生产者） |
| emit 回调 | 传菜窗口 | 后厨（turn）做好一道菜就往窗口一放（`emit(ev)`），前厅（REPL）取走就上桌。窗口只有一个，但足够了——不需要广播系统 | `pcode/core/turn.py` 的 `TurnHooks.emit`、消费端 `pcode/shell/repl.py` 的 `_render` |
| compact | 会议纪要 | 三小时的会（几十条对话）没人再听录音，秘书把录音压成一页纪要（任务目标/已完成/未完成），以后开会只带这一页。纪要写废了（模型失败/用户 Ctrl+C）就还用原录音——原始材料永不销毁 | `pcode/core/compact.py` 的 `compact_context`、手动入口 `pcode/plugins/commands/compact.py` |

## 3. 最常见的误解

**误解一："事件模型必须上消息总线 / 观察者框架 / asyncio，否则做不了。"**

不对。一个 `emit` 回调就是完整的事件出口。`pcode/core/turn.py` 里事件生产是纯粹的
同步函数调用：

```python
emit(TurnStart(id=str(uuid4())))
emit(User(text=line))
...
on_text=lambda delta: emit(TextDelta(delta=delta)),
```

`pcode/shell/repl.py` 的 `_render` 拿到就渲染。总线的附加价值——多消费者、跨进程、
背压、动态订阅——在"一个壳 + 同步单线程"的场景里一样都不存在。加消费者（比如审计
落盘）时先想想：把 `emit` 包一层（先写文件再转发给渲染）就够了，不需要任何框架。

**误解二："compact 就是删掉旧消息。"**

不是删除，是换表示。`compact_context` 把 `messages[1:]` 整体替换为一条 user 摘要
消息（system 保留），任务目标与未完成事项还在——丢的是原文细节。纪律是"成功才动
历史"：`pcode/core/compact.py` 里摘要请求失败、模型返回空串、用户 Ctrl+C，全都发生在
替换之前，`app.messages` 原封不动（`test/test_compact.py` 的四个用例锁死这一点）。

**误解三："被打断的一轮也应该收到 turn_end 事件，否则消费者状态不一致。"**

tcode 确实发 `turn_end(aborted/error)`；pcode 刻意不发——同步模型里
`KeyboardInterrupt` 直接穿透 `run_user_turn`（先断尾修复、落盘，再上抛），壳用异常
类型区分展示（`pcode/shell/repl.py` 的 `except KeyboardInterrupt`）。事件流在异常
路径上是"断"的，这是文档化的取舍（README"与 tcode 的已知差异"第 2 条），消费者必须
把"异常上抛"理解为终态信号，与 `turn_end` 互斥。

## 4. 本仓库真实代码怎么读（按一轮对话的生命周期）

| 步骤 | 发生了什么 | 位置 |
| --- | --- | --- |
| 1. 轮前治理 | `estimate_tokens > config.context_limit` 时先 `compact_context`（失败退 `trim_context`，裁了才发 `Trimmed`） | `pcode/core/turn.py` 的 `run_user_turn` 开头 |
| 2. 事件开场 | `emit(TurnStart(id=uuid))` → `emit(User(text))` | `pcode/core/turn.py` |
| 3. 工具循环回调 | 模型要工具：`on_tool_call(call_id, name, args)` → 事件 `ToolCallEvent`；执行完：`on_tool_result(call_id, name, result, ms)` → 事件 `ToolResult`（summary 取结果首行）；正文增量 `on_text` → 事件 `TextDelta` | `pcode/core/agent_loop.py` 的 `TurnDeps`、`run_turn` |
| 4. 收尾 | 无异常 → `emit(TurnEnd(reason='completed'))`；异常 → 断尾修复（补"（用户中止，未执行）"占位）→ 落盘 → `emit(TurnEnd(aborted/error))` → 上抛 | `pcode/core/turn.py` 的 `except BaseException` 块 |
| 5. 壳消费 | `match ev:` 四个分支：TextDelta 直写 stdout、ToolCall 打 `⚙ 名字 参数`、ToolResult 打 `↳ 首行 (ms)`、Trimmed 打灰字提示；`turn_start`/`user`/`turn_end` 无专属展示 | `pcode/shell/repl.py` 的 `_render` |
| 6. compact 本体 | ≤5 条抛"对话太短"；`messages[1:]` 拼成 `role: content` 转写 → 摘要提示词（中文、只输出正文、保留目标/步骤/路径/未完成）→ 成功才替换为 `[system, "[此前对话的摘要……]"]` | `pcode/core/compact.py` 的 `compact_context`、`_transcript_line` |
| 7. 节省计量 | 前后各估一次 token，`saved_tokens = max(0, before - after)`；估算公式与 trim 同一份（字符/3 上取整 + 每条 8，tool_calls 参数计入） | `pcode/core/trim.py` 的 `estimate_tokens`（compact 直接复用） |
| 8. 手动入口 | `/compact` 命令：成功打"已压缩：……节省约 N tokens"，失败打"压缩未执行：原因"且不上抛 | `pcode/plugins/commands/compact.py` |

对应测试（先红后绿的契约锁）：`test/test_events.py`（规范序列
`turn_start→user→tool_call→tool_result→text_delta→turn_end`、工具执行后中断、
工具执行中中断补占位、普通错误路径）、`test/test_compact.py`（替换+节省>0、
≤5 拒绝原状、失败原状、Ctrl+C 原状）。

## 5. 与其他语言对照：为什么同步 Python 做不了轮中真取消

| 主题 | tcode（TS，async 世界） | pcode（Python，同步阻塞） |
| --- | --- | --- |
| 事件形态 | 判别联合：`{ type: 'tool_call', ... }` 字面量类型 | 每变体一个 dataclass + `ClassVar type` 固定标识 |
| 消费方式 | `switch (ev.type)` | `match ev:` 类模式（`case ToolResult(summary=s, ms=ms)`） |
| 轮中取消 | `AbortSignal`：fetch 的每个 await 点都能响应，异常被译成 `turn_end(aborted)` | 做不到：阻塞在 `http` 流读或 `tool.run()` 里，没有事件循环可响应取消；Ctrl+C 靠 Python 信号机制注入 `KeyboardInterrupt`，粒度只有"整轮炸掉" |
| compact 调用 | `await compactContext(app, { signal })` | 普通函数 `compact_context(app)`；`signal` 参数仅占位对齐形状 |
| 取消后的世界 | 本轮中止，REPL 继续下一轮 | 进程退出（退出前断尾修复已保证会话文件合法） |

同步模型做不了轮中真取消的根因：取消的本质是"在任意挂起点安全地跳转回调度器"，
而同步代码没有调度器——线程阻塞在 socket `read()` 上时，Python 主线程连"检查一下
该不该停"的机会都没有。Ctrl+C 的 `KeyboardInterrupt` 只能落在一个字节码边界，落在
哪全看运气（可能在工具执行中途、可能在 SSE 解析半行），所以 pcode 只能选择
"整轮作废 + 修复落盘 + 退出"这一种安全语义。

什么条件下值得上 asyncio：需要**轮中真取消**（流式中 Ctrl+C 只中止本轮、接着问下一句）、
**并发工具调用**、或 **web 壳的多订阅者 SSE** 时。代价要一次付清：SSE 解析换成
async 流、权限确认的 `input()` 要丢进 `loop.run_in_executor`、`run_turn`/
`compact_context`/`run_user_turn` 全链路 async 化——tcode 的 `AbortSignal` 正是
async 世界的一等公民。只有第一条需求真实出现时才值得，为"架构先进"而 async 化是
负收益（本项目 README 已把它列为已知局限而非缺陷）。

## 6. 从读完到掌握的下一步路径

1. **加一个事件消费者（体验事件模型的红利）**：把 `emit` 包一层——先按行把事件写成
   JSONL（审计/回放），再转发给 `_render`。只改 `pcode/shell/repl.py` 的 `start_repl`，
   核心零改动；这就是"壳/审计/回放是并列消费者"的含义。
2. **接入 Usage 事件**：`pcode/kernel/types.py` 的 `Usage` 已是契约占位；给
   `pcode/providers/openai.py` 的 `chat()` 加 `on_usage` 回调（SSE 的 usage 字段已在
   响应里），`pcode/core/turn.py` 转发为 `emit(Usage(...))`。
3. **升级 compact：摘要 + 最近 N 条**：`pcode/core/compact.py` 目前是纯摘要（无配对
   边界问题）；真实需要更细的上下文时，把 `messages[1:][:-N]` 换摘要、保留最近 N 条，
   注意 assistant↔tool 配对不能被截断。
4. **asyncio 对照实验**：fork 一份 `pcode/core/agent_loop.py` 改 async + `asyncio.sleep`
   模拟 provider，体验 `Task.cancel()` 在每个 await 点的取消粒度，再回头看本指南第 5
   节的取舍——局限是怎么来的、什么时候值得解除。
5. **验收自查**：`python -m unittest discover -s test -v`（25 个用例）与
   `python test/smoke.py`（五场景）全绿；再用真实模型端点验证一次 `/compact` 的
   端到端效果（长对话压缩后模型仍记得任务目标）。
